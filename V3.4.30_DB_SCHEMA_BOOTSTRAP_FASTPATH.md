# MarketPredictor v3.4.30 — DB Schema Bootstrap Fast Path

## What was wrong

The application accumulated a large ordered `init_db()` migration containing roughly 250 idempotent `CREATE TABLE`, `ALTER TABLE`, index, and cleanup statements. That routine was being executed on every Gunicorn process boot, even when PostgreSQL already contained the complete current schema.

On Render, the user's logs showed healthy PostgreSQL authentication and short-lived sessions, while the application reported roughly 0.18 seconds per schema step. That is consistent with repeated client/server round trips rather than a PostgreSQL connectivity outage.

The interim v3.4.29.2 batching change grouped statements into multi-statement `execute()` calls to reduce round trips. It was not retained because it obscured the exact migration step when a DDL statement waits on a lock or fails.

## Fix

v3.4.30 introduces a persistent `marketpredictor_schema_state` marker and a metadata-only verification fast path.

- A normal restart checks the schema marker plus the required table/column contract and becomes `READY` without replaying the full migration.
- Existing v3.4.x databases that predate the marker can be adopted automatically when the full required schema contract is already present.
- A database that is incomplete or on an older schema contract still runs the ordered legacy migration.
- A successful full migration stamps the current schema version.
- Migration failures retain per-step diagnostics and attempt a best-effort `pg_stat_activity` blocker diagnostic.
- Database-backed HTTP APIs continue to fail fast with `database_initializing` while genuine first-time migration is running.

## Expected boot behavior

Existing/current database:

`PostgreSQL CONNECTED -> schema fast-path check -> READY`

Fresh/partial database:

`PostgreSQL CONNECTED -> full schema migration -> schema marker -> READY`

The full migration remains background work, so `/`, `/healthz`, `/api/market-status`, and `/api/db-status` do not wait for it.
