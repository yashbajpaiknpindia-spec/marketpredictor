# Market Predictor v3.2.5: historical export memory fix

This package updates the latest v3.2.4 source. It is ready to deploy; this work did not change the running Render service.

## Deploy

1. Extract this ZIP and copy its contents into the existing repository, replacing matching files. Keep your deployment secrets in Render. Include the new `export_streaming.py`, `gunicorn.conf.py`, and updated `requirements.txt`.
2. Commit and push the changed source to the repository connected to your Render service.
3. Use build command `pip install -r requirements.txt`.
4. Set the Render start command to:

```sh
gunicorn app:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --worker-class gthread --timeout 120
```

The included Gunicorn configuration also supplies these defaults if your existing command is only `gunicorn app:app`. Explicit dashboard command flags take precedence, so remove any conflicting worker count. The exporter uses in-process background jobs and requires one web worker.

For a 512 MB service, set:

```text
HISTORICAL_EXPORT_MEMORY_LIMIT_MB=512
HISTORICAL_EXPORT_MEMORY_RESERVE_MB=128
HISTORICAL_EXPORT_WORKERS=1
HISTORICAL_EXPORT_1M_SCRIPS_PER_CALL=1
HISTORICAL_EXPORT_PERSIST_DB=true
HISTORICAL_EXPORT_DB_KEEP=1
HISTORICAL_EXPORT_DB_MAX_MB=180
```

The updated render.yaml includes the memory settings. Editing that file alone does not update an independently configured existing service; check its Environment and Start Command in Render. Use your actual memory allocation if it differs from 512 MB.

5. Deploy and start a NEW historical export. A running export killed by the previous process cannot be resumed from its partial ZIP. Existing completed PostgreSQL-backed exports remain compatible.
6. Wait for saving to finish, then Download. An export now remains active during database saving, preventing an overlapping export. Browser byte-range downloads are supported.
7. Check the downloaded `manifest.json`: `exporter_version` must be `v3.2.5-streamed-memory-safe-export`. Inspect `quality/fetch_failures.csv`, `quality/date_completeness.csv`, and `reference/fallback_provider_attempts.csv` for actual provider gaps.

## What was fixed

- Upstox's compressed NSE catalogue was fully decompressed, decoded and cached, including derivatives. It now downloads to a temporary file, parses records incrementally, and keeps only index entries.
- Dhan's entire instrument CSV was retained as row dictionaries. Only index entries are retained now, with streamed download and parsing.
- Both fallback paths loaded catalogues before checking credentials. Missing credentials now produce an explicit status without that download.
- Fallback index ranges are staged on disk in seven-day windows. Equity fallback fetches only one missing date at a time. Failed stock dates are recorded and do not prevent later dates from being attempted.
- Historical/event HTTP JSON responses are bounded to 8 MiB of decoded HTTP body before parsing. Unexpectedly oversized data is reported as a failure, never silently truncated. Instrument catalogue downloads have a separate 128 MiB transfer cap and incremental gzip/JSON parsing.
- Quality and anomaly records are stored in a bounded-cache SQLite spool and streamed into the ZIP.
- Finished Future results are released before the next request. Routine full-heap collection runs at most once per five seconds; pressure handling still collects immediately.
- Memory checks consider container working-set use, including other processes. All intervals use one provider request and one stock per call on containers up to 1 GB. Estimates now use that actual batching.
- The job remains active until database persistence finishes. Archive restoration is serialized and checks the restored byte count before publishing the local file.
- Default Gunicorn settings use one process with four threads; status polling can continue during downloads/restoration.

The historical archive layout, raw candle values, provider precedence and trading strategy rules are preserved. Existing explicit data-hygiene rules remain in place. Optional extra datasets report failures or memory limits in dataset status.

## Verification

- 23 automated regression cases passed.
- All root Python files and new tests compile.
- Gunicorn configuration/application import check passed.
- Offline stress test used the real Flask application and export implementation with synthetic provider data under a 512 MiB address-space limit.
- Parsed a synthetic catalogue containing 500,000 irrelevant derivative records (~285 MiB uncompressed); retained one index. Process RSS after catalogue parsing was ~116 MiB.
- Exported 6,187,500 candles: 250 stocks × 66 sessions × 375 candles.
- Verified 16,500 stock-day CSVs, quality counts, ZIP CRCs and unique archive entry names.
- Downloaded the entire 109,040,187-byte archive through the Flask endpoint and verified a 1,024-byte HTTP 206 range response.
- Process memory was approximately 132 MiB. The complete offline stress exercise took 29.65 seconds with network calls and deliberate provider pacing disabled; this is NOT a live-provider timing estimate.

Detailed measurements: `V3.2.5_STRESS_RESULTS.json`.

To repeat locally after installing requirements and pytest:

```sh
PYTHONPATH=. python -m pytest -q tests/test_export_memory.py
OPENBLAS_NUM_THREADS=1 PYTHONPATH=. python tests/stress_export_memory.py
```

## Validation limits

Live Render, broker-authenticated downloads and real PostgreSQL persistence were not accessible here. Persistence sequencing, restore integrity and concurrency were tested with controlled database doubles. The stress run includes the real application baseline but not simultaneous live market scans; its process limit is not a complete Render-container reproduction. Other workloads, credentials, provider throttling and data availability can still affect a live run. A post-deploy export is the remaining production check.

Completed archives keep the existing PostgreSQL persistence cap and retention policy. Larger archives or database failures remain downloadable from the current runtime but may not survive a redeploy; the UI reports this. Memory protections cannot resume an export across an unrelated host restart.
