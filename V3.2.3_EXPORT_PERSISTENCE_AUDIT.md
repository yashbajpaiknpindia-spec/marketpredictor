# V3.2.3 Historical Export Persistence / Compactness Audit

## Problem reproduced from Render logs
- A historical-export job returned HTTP 200 while the original gunicorn process was alive.
- Render then started a new gunicorn process.
- The same job id immediately returned HTTP 404.
- Root cause: live job state was in process memory and the archive/meta lived under the normal Render runtime filesystem, which is ephemeral across a redeploy/replacement instance.
- A browser refresh alone is not destructive. The backend restart/deploy is the destructive event.

## Changes
### 1. Persistent job metadata
Historical export metadata is mirrored to PostgreSQL (`DATABASE_URL`) in `historical_export_jobs`.
- Active progress is checkpointed at most every ~5 seconds.
- After a restart, interrupted pending/running jobs remain visible and are marked `error / interrupted` instead of vanishing with 404.

### 2. Persistent newest completed ZIP
The completed ZIP is stored in PostgreSQL chunks in `historical_export_archive_chunks`.
- Default: persist newest 1 completed archive.
- Default maximum archive size: 180 MB.
- Chunk size: 4 MB.
- If the local Render file is gone after redeploy, the download endpoint restores the ZIP from PostgreSQL automatically.
- Older DB archives are deleted automatically to protect database storage; metadata remains.

Environment controls:
- `HISTORICAL_EXPORT_PERSIST_DB=true`
- `HISTORICAL_EXPORT_DB_KEEP=1`
- `HISTORICAL_EXPORT_DB_MAX_MB=180`
- `HISTORICAL_EXPORT_DB_CHUNK_MB=4`

### 3. Compact ZIP mode
New default `Compact ZIP` mode stores candle rows as:

`epoch,open,high,low,close,volume`

instead of:

`timestamp,open,high,low,close,volume,epoch`

The ISO timestamp was redundant because it is exactly derivable from epoch using Asia/Kolkata. OHLCV and provider epoch are unchanged.

Empirical test on 1,500 real stock-day files from the user's 1-minute export:
- Original compressed sample: 9,620,547 bytes
- Compact compressed sample: 7,247,286 bytes
- Reduction: ~24.7%

For the same row count as the prior ~120.3 MB export, the estimator is now ~90.2 MB in compact mode. Actual size varies with prices/volume/compressibility.

### 4. Live UI data plan
During an export the completeness table is no longer hidden until completion.
It shows requested datasets up front (`REQUESTED`) including:
- equity OHLCV
- NIFTY / India VIX
- sector indices
- corporate actions
- announcements / results
- bulk/block deals
- FII/DII
- global context / GIFT NIFTY
- known unsupported historical microstructure / point-in-time data

At completion the planned rows are replaced by actual source/status/row-count/failure details.

### 5. Persistence status in UI
Progress now includes a Storage card:
- `building-local`
- `postgres+local` / `persistent`
- `local-ephemeral`

Recent jobs show `persistent` when the ZIP was archived in PostgreSQL.

### 6. Deployment warning
The UI now explicitly warns that a running export cannot continue through a redeploy. Completed exports are persisted, but the current Python worker/thread is terminated by deployment. Do not redeploy while a build is running.

### 7. Runtime NameErrors fixed
The Render log exposed two unrelated missing functions:
- `start_exit_monitor_worker`
- `get_weekly_goal_status`

Both are now defined. The Position Guard worker has start/stop/status functions and a guarded background exit-evaluation loop. Weekly guard reads closed-position net P&L plus API costs for the current IST week and exposes target/loss guard status.

## Validation
- `python -m py_compile app.py historical_export.py historical_fallbacks.py historical_extras.py`: PASS
- Extracted browser JavaScript `node --check`: PASS
- Compact serializer preserves epoch + OHLCV: PASS
- Compact size estimate for 225 stocks / 61 sessions / 1m: ~90.2 MB vs ~120.3 MB verbose estimate.
- Existing provider fallback/data acquisition code retained.
- No trading simulation was run as part of this patch.

## Important operational behavior
A Render redeploy terminates an in-progress background thread. This patch preserves its status and prevents a misleading 404, but it does not magically continue that exact in-flight API request sequence. Start/restart the export after deployment. Once it reaches `completed` and UI shows `persistent`, the ZIP survives later redeploys.
