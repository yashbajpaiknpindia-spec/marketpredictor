# MarketPredictor v3.4.0 — Database Pool Fix

## Problem addressed
PostgreSQL accepted connections in milliseconds, but the application repeatedly opened and closed SSL connections and treated schema migration readiness as if it were connectivity.

## Changes
- Added a thread-safe psycopg2 connection pool (lazy, 1–5 connections by default).
- `get_db_connection()` now borrows from the pool; existing `conn.close()` calls return connections to the pool.
- Database connectivity probe and schema migration use dedicated direct connections and do not consume pool capacity.
- Connectivity and schema readiness remain separate states.
- `/healthz` reports pool initialization/borrowed counts and connection/schema timing.
- The global request gate no longer blocks all API requests merely because schema migration is still running; only true database-offline/disabled states are globally rejected.
- Existing Replay/20-strategy engine/UI preserved.

## Environment knobs
- `DATABASE_CONNECT_TIMEOUT_SECONDS` (default 5)
- `DATABASE_POOL_MAX_CONNECTIONS` (default 5)
- `DATABASE_RETRY_SECONDS` (default 5)
- `DATABASE_SCHEMA_RETRY_SECONDS` (default 30)
- `DATABASE_STATEMENT_TIMEOUT_MS` (default 30000)
- `DATABASE_LOCK_TIMEOUT_MS` (default 5000)

## Expected logs
```text
[DB] connection attempt #1 starting
[DB] PostgreSQL CONNECTED in 0.xxxs; SELECT 1 passed
[DB] connection pool created (max=5)
[DB] connection pool warm and ready for API traffic
[DB] schema initialization attempt #1 starting
...
[DB] READY: schema complete in X.xxxs
```

A green DB light means PostgreSQL connectivity is confirmed. Schema readiness is tracked separately.
