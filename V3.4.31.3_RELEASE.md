# MarketPredictor v3.4.31.3

## Database bootstrap worker lifecycle fix

This release fixes the production failure where the bootstrap worker could start and exit almost immediately with `schema_attempts=0`, causing three supervisor starts to terminate without ever reaching PostgreSQL schema migration.

### Root cause
The schema worker had two ownership gates: the live worker supervisor and the legacy `_DB_INIT_STARTED` boolean. A stale `_DB_INIT_STARTED=True` state could survive an application lifecycle boundary while the actual worker thread was gone. A newly supervised worker then entered `_initialize_database_background()`, saw the stale flag, and returned immediately before schema attempt #1.

The production diagnostic matched this path: worker start and exit timestamps were separated by about 0.4 ms, with zero schema attempts, no crash exception, and three worker starts.

### Changes
- Removed `_DB_INIT_STARTED` as a second early-return gate for the schema worker.
- The dedicated `_DB_BOOTSTRAP_START_LOCK` / worker supervisor is now the sole lifecycle gate for the bootstrap thread.
- `_DB_INIT_STARTED` remains an activity/diagnostic flag rather than an independent worker-ownership mechanism.
- Added a regression test reproducing the exact stale `_DB_INIT_STARTED=True` production state.
- Retained worker liveness/crash/stall supervision from v3.4.31.2.
- Retained PostgreSQL advisory locking, bounded migration attempts, and schema fast-path verification.
- No PostgreSQL schema version change is required.

### Expected production behavior after redeploy
The bootstrap status should progress from `CHECKING` / `schema_pending` to either:
- `MIGRATING` with `schema_attempts >= 1`, or
- `READY` / `ready_fastpath` if the existing schema is already complete.

It should no longer cycle through worker starts with `schema_attempts=0` merely because `_DB_INIT_STARTED` is stale.
