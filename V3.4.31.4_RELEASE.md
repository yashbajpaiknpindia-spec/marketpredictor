# MarketPredictor v3.4.31.4

## Database connection churn fix

### Production symptom
The bootstrap worker was fixed in v3.4.31.3, but PostgreSQL logs still showed repeated authentication followed by short-lived sessions. The application could show `DB: Connected` and then appear to disconnect/reconnect repeatedly.

### Root cause
`_ensure_db_pool()` created the psycopg2 `ThreadedConnectionPool` with `minconn=0`. In psycopg2, `putconn()` only retains idle connections while the pool has fewer than `minconn`; with `minconn=0`, returned connections are discarded/closed. Therefore every `/api/db-status` probe performed a fresh PostgreSQL connection, `SELECT 1`, and disconnect cycle.

### Fix
- Changed the shared pool from `ThreadedConnectionPool(0, maxconn, ...)` to `ThreadedConnectionPool(1, maxconn, ...)`.
- Kept additional connection creation lazy up to `maxconn`.
- Updated the offline pool regression model to require `minconn=1`.
- Added a static regression test that prevents reintroducing `minconn=0`.
- Kept the v3.4.31.3 worker lifecycle, advisory-lock, bounded-attempt, and schema fast-path fixes unchanged.

### Verification
- Focused DB/bootstrap + pool suite: 19 passed.
- Wider application test suite excluding only `tests/test_export_memory.py`: 100 passed.
- Python compilation: passed.
- No PostgreSQL schema version change.

### Expected production behavior
The first pool initialization opens the persistent connection. Repeated UI status probes reuse the pooled connection instead of creating a new PostgreSQL SSL session every 3 seconds. PostgreSQL logs should therefore stop showing the previous repeating authentication/disconnection pattern from status polling.
