# MarketPredictor v3.4.31.5

## Database connection churn: root-cause fix (pool exhaustion / teardown)

### Symptom
PostgreSQL logs showed `marketpredictor_user` sessions authorizing and disconnecting
every 1-60 seconds, and the UI DB indicator flapping, even after v3.4.31.4
(`minconn=1`).

### Root causes (all reproduced against a real PostgreSQL 16 server)
1. **Idle retention capped at `minconn`.** psycopg2 `putconn()` keeps a returned
   connection only while `len(idle) < minconn`; every other one is closed. With
   `minconn=1`, any concurrency above 1 closes the extras and re-handshakes
   (TCP+TLS+md5) on the next burst. (v3.4.31.4 fixed the single-threaded probe
   case only.)
2. **Pool exhaustion tore the whole pool down.** `get_db_connection()` treated any
   `getconn()` failure, including `PoolError: connection pool exhausted`, as a
   stale pool and called `closeall()`, which closes connections *in use by other
   threads*. Every in-flight request then failed with `connection pool is
   closed`, and everything reconnected. Original code under 12 threads x nested
   checkouts: `exhausted` -> 10 threads crash with `pool is closed`.
3. **Nested checkouts on a pool of 5.** 28 functions hold one connection while
   calling helpers that borrow another (up to 3 deep, e.g. trading dashboard ->
   `evaluate_open_positions_for_exits` -> `get_open_positions`). 4 request threads
   + background loops reach "everyone holds one, waits for a second" quickly, which
   is what triggers (2).
4. **`with conn:` returned the connection to the pool** (wrapper `__exit__`).
   `with conn:` in psycopg2 scopes a transaction. Loops with a per-iteration
   `with conn:` (`evaluate_open_positions_for_exits`, `run_accuracy_check`), helpers
   that receive `conn` as an argument, and the error path in
   `_agent_apply_proposal` kept using a connection another thread could already
   own (cross-thread commit/rollback risk).

### Fix
- New `db_pool.py` (`ManagedPool`, `PooledConnection`), used by `app.py`:
  - retains **all** healthy idle connections, recycled only after 300 s idle;
  - **waits** (bounded, default 15 s) for a slot; never closes in-use connections;
  - separate **nested reserve** so threads already holding a connection can never
    deadlock behind top-level waiters;
  - validates connections idle > 5 s with `SELECT 1`; a dead one is replaced
    individually (server restart / idle NAT timeout);
  - `with conn:` now only scopes the transaction; `close()` returns to the pool;
    use after return raises `InterfaceError` instead of silently sharing;
  - `__del__` safety net returns (and logs) a connection that was never closed;
  - `opened` counter = real PostgreSQL connections ever created.
- TCP keepalives on all connections (`keepalives_idle=30`).
- Status probe: 5 s result cache; pool saturation is reported as *busy*, not as a
  disconnection.
- Explicit `close()` added to 3 call sites that relied on with-exit; fixed the
  `_agent_apply_proposal` error path.
- `/healthz` and `/api/db-status` now include `db_pool` stats.

### Config (all optional)
| env | default |
|---|---|
| `DATABASE_POOL_MAX_CONNECTIONS` | 8 (top-level slots) |
| `DATABASE_POOL_NESTED_RESERVE` | = above (extra slots for nested checkouts) |
| `DATABASE_POOL_CHECKOUT_TIMEOUT_SECONDS` | 15 |
| `DATABASE_POOL_IDLE_TTL_SECONDS` | 300 |
| `DATABASE_POOL_VALIDATE_AFTER_SECONDS` | 5 |
| `DATABASE_PROBE_CACHE_SECONDS` | 5 |

Worst case 16 connections per instance (lazy). Keep `instances x 16` below the
database plan's connection limit.

### Verification
- Full suite: 109 passed (100 existing + 9 new real-PostgreSQL pool tests; set
  `TEST_DATABASE_URL`, skipped otherwise). Includes a control test proving the
  stock pool churns under the same load.
- End-to-end boot of `app.py`: 960 status/health requests -> 1 pooled connection;
  12 threads x 20 nested checkouts -> 16 sessions total (peak concurrency), all
  retained, `in_use=0`, borrowed counter 0.

### Not caused by this application
Sessions for user `postgres` from a single IP every 60 s (3.0 s each, plus a
`client=[local]` line) come from the managed-database platform's own monitoring,
not from this app. They cannot be removed from application code.
