# MarketPredictor v3.4.34.16 — self-healing database bootstrap

## Why this build exists

A fresh PostgreSQL database could be reachable while the background schema worker was still starting, waiting on an overlapping Render instance, or retrying a DDL operation. The previous supervisor could misclassify a live worker that had not yet incremented its schema-attempt counter as stalled and could eventually leave the service in a terminal schema-error state.

## Changes

- Fresh/new database bootstrap now retries schema creation indefinitely by default until the required schema is ready.
- Terminal schema failure is opt-in through `DATABASE_SCHEMA_FAIL_CLOSED=1`.
- The schema migration connection uses `statement_timeout=0`, `lock_timeout=0`, and `idle_in_transaction_session_timeout=0` because it is a dedicated migration connection and must not be killed by request-time limits.
- A live bootstrap worker is never converted into `bootstrap_worker_stalled_before_schema` merely because the first migration attempt has not started yet.
- The bootstrap supervisor automatically recovers from unexpected Python worker exceptions.
- Transient schema failures are reported as `RETRYING` / `MIGRATING`, not as a permanent DB outage.
- Existing databases retain the compatibility-first, non-destructive startup path.
- No data deletion or schema reset is performed.

## Operational outcome

For a healthy new Render PostgreSQL database the application keeps converging automatically through connection, advisory-lock acquisition, full schema creation, verification, and READY. A transient SSL disconnect, competing migrator, or restart no longer exhausts a small retry budget and strands the application in a terminal schema error.
