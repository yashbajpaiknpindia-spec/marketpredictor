# v3.4.34.10 — Large-data storage and memory architecture

## The two different 1 GB limits

Keep **web-service RAM** and **PostgreSQL disk/storage** separate. A web service reaching ~96% of a 1 GB RAM limit is a compute-memory problem; increasing Postgres storage does not fix it. A ~96% PostgreSQL storage figure is a database-capacity problem; increasing web RAM does not fix it.

## Recommended production design

**PostgreSQL = control plane**
- users/settings
- job state/progress
- coverage inventory
- symbol/ISIN resolution
- dataset manifests/fingerprints
- evidence summaries/decision audits
- paper/live/replay records

**Large-data store = data plane**
- 1-minute candle blobs by dataset/ticker/day
- historical export ZIP/Parquet artifacts
- large reference datasets
- immutable raw research files

For the current single-instance architecture, a Render persistent disk is the simplest integrated option. For a web service + background worker architecture, an S3-compatible object store (for example S3/R2) is the cleaner long-term option because both services can access the same immutable files. Render documents persistent disks as persistent storage for paid web/private/background services; only data below the mount path persists.

## Memory rule

The web service must never materialize an entire year × 250-symbol × 1-minute dataset. Acquisition should use bounded provider batches, persist each batch immediately, and release DataFrames after each batch. Replay should load only selected sessions/segments.

## v3.4.34.10 safeguards

- Fixed the Storage `_format_bytes` runtime error.
- Storage reports web-service cgroup memory separately from PostgreSQL size.
- New heavy Market Data jobs are blocked when service memory is critically high.
- Provider fetch concurrency is reduced under memory pressure.
- Default DB pool size is reduced for a 1 GB web service.
- Market-data acquisition uses a presence-only cache scan and does not materialize stored candle JSON merely to discover gaps.

## Migration rule

Do **not** drop or recreate the existing database. Clean only verified rebuildable records first. Then migrate large candle blobs/archive files incrementally to the data-plane backend, with checksum verification before deleting the old JSONB/blob copy.
