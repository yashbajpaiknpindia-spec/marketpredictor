# MarketPredictor v3.4.34.4 — DB safety and bootstrap compatibility

## Problem diagnosed

The production logs showed PostgreSQL connectivity was healthy, but the application entered `WAITING_FOR_MIGRATOR` because another process held the schema advisory lock. The application then returned 503s while waiting for the migration worker. PostgreSQL itself continued accepting and authenticating connections.

The database logs also showed normal authenticated connections plus one `unexpected EOF on client connection with an open transaction`; that is a connection/session event, not evidence that the database lost data.

## Safety changes

- Existing data-bearing databases no longer run the legacy monolithic `init_db()` migration just because a new additive table/column is missing.
- Stable legacy core tables are checked first. If they exist, the app enters **ready_compatibility** and keeps the application available.
- Current Market Data, Evidence, and AI proposal schema objects are repaired with additive `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN IF NOT EXISTS` operations only.
- The compatibility repair runs in the background under the existing advisory lock, without blocking normal application startup.
- A new deployment cannot turn a healthy existing database into a global 503 simply because a new column is pending.
- Advisory-lock holder diagnostics now report PID, state, client and query when another migrator owns the lock.
- The waiting loop for truly fresh/incomplete databases is slowed to avoid connection/reconnect storms.
- The existing schema-state marker is stamped only after the full schema contract is observed.

## Data preservation

This release does not add any startup `DELETE`, `TRUNCATE`, or destructive rewrite to the compatibility path. Existing rows are not rewritten by the compatibility repair.

## Important deployment behaviour

For an already-populated production database: application readiness is now decoupled from full schema convergence. Endpoint-level self-heal remains available for Market Data and Evidence tables.

For an empty/new database: the existing full initialization path remains responsible for creating the entire application schema.
