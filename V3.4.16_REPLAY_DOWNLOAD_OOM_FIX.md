# v3.4.16 — Replay Download OOM / Worker Restart Fix

## Problem observed

Replay #24 itself reached a valid results page, showing:

- Starting capital: ₹2,00,000
- Ending capital: ₹1,97,310
- Net P&L: -₹2,690
- 27 trades
- 5 selected sessions (21–25 Sep 2026)
- Data source summary: **0 Export Data ticker-days, 1,356 Replay-cache ticker-days, 0 newly fetched, 240 reference datasets**

The failure happened when requesting the **Download** artifact for the newer replay. The web UI then showed a red `Database connection error: Web service is unreachable — retrying automatically.` banner.

## Log interpretation

The supplied PostgreSQL log excerpt contains repeated successful connection/authentication/authorization events followed by normal short-lived disconnections. It does **not** contain evidence such as:

- `FATAL`
- `PANIC`
- `database system is shutting down`
- `database system is starting up`
- PostgreSQL crash/recovery messages

The excerpt therefore does not establish that PostgreSQL itself restarted. Combined with the UI wording (`Web service is unreachable`) and the fact that older replay downloads still work, the most plausible failure boundary is the single Render gunicorn worker being terminated/restarted during the large export request. The red DB badge is then a downstream symptom because the browser can no longer reach the web service's DB-status endpoint.

## Root cause in the old downloader

The previous path did all of the following in one request:

1. `SELECT ... FROM intraday_replay_candle_cache ...`
2. `fetchall()` — all candle rows in a Python list.
3. Convert each candle row into a JSON string.
4. Store all JSONL text in the `files` dictionary.
5. Build the ZIP inside `io.BytesIO()`.
6. Call `buf.getvalue()` to create another full archive bytes object for Flask.

That means one large replay could exist simultaneously as database result objects, Python dictionaries, JSON text, compressed ZIP buffers and a second full byte copy. Replay #24's 1,356 ticker-days made that path materially riskier than older/smaller replays.

## v3.4.16 implementation

### 1. Bounded database reads

The candle cache is exported with a named PostgreSQL cursor and `fetchmany(25)` batches. The process never creates a Python list containing the entire candle cache.

### 2. Disk-backed ZIP

The ZIP is written to a temporary file with ZIP64 enabled. `market_candles.jsonl` is written directly into the ZIP entry while rows are being fetched.

### 3. Hashes remain deterministic

A SHA-256 digest is updated as each JSONL row is written, so `manifest.json` still records the checksum of the exact candle artifact.

### 4. No second whole-archive memory copy

The completed ZIP is returned with Flask `send_file()` instead of `BytesIO().getvalue()`.

### 5. JSON export safety

`format=json` now intentionally omits the full market candle payload and reports that the complete candle artifact is available in the ZIP. This prevents a JSON request from recreating the same giant serialization/memory spike.

## What was not changed

- 20 strategy definitions
- strategy independence
- strategy attribution logic
- entry timing
- chronological replay execution
- slippage/cost model
- capital guard
- position sizing
- stop/profit-protection behavior
- historical candle values
- cache reuse policy

Only the **download transport/materialization path** changed.
